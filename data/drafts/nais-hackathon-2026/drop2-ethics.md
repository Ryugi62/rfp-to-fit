**팀명: 루미아** · 세부주제: 연구 기획·탐색 + 성과 작성·연구행정(통합형)

# [주제명] 평가위원의 눈으로 빈칸을 먼저 찾는 R&D 기획 에이전트 "RFP-to-Fit"

# [주제 요약]
국가 R&D 공고(RFP)를 넣으면 자격·요건과 평가지표를 구조화하고, 관점이 다른 **가상 평가위원 에이전트 여럿이 연구자 초안을 독립 채점**해 "어느 지표에서, 왜, 근거가 비는가"를 대조표와 결핍 목록으로 보여주는 에이전트다. 채워야 할 근거의 종류와 위치를 지정한다. 공개 RFP 3건과 사람이 만든 정답표로 정확도를 검증해 시연한다.

# 1) 연구 문제 및 제안 배경

**문제 장면.** 공고가 뜨면 연구자는 짧은 기간에 요건 확인, 선행연구·특허 조사, 제안서 작성, 심사기준 대조를 동시에 한다. 가장 비싼 실패는 "아이디어가 나빠서"가 아니라 **"심사기준을 잘못 읽어서"** 생긴다. 평가지표의 어휘와 연구자의 서술 어휘가 다르고, 요건(참여 제한·필수 첨부·기간)은 본문·첨부·FAQ에 흩어져 있어 결핍이 제출 직전에야 드러난다. 우리 팀은 2026년 공모·지원사업 공고 400여 건을 직접 읽고 자격·요건을 판정하면서 이 패턴을 반복해서 겪었다.

**왜 지금인가.** 정부 R&D 투자는 2026년 예산안 기준 35조 원 규모이고, 공고·과제 정보는 NTIS와 IRIS에 구조화되어 공개돼 있다. 긴 공고문과 심사표를 안정적으로 읽고 대조하는 언어모델도 상용화됐다. 즉 **데이터는 이미 공개돼 있고, 평가위원의 눈으로 읽어 주는 도구만 없다.**

**병목을 소급하면 진짜 사용자가 보인다.** 왜 떨어지는가 → 지표와 서술이 어긋나서 → 왜 어긋나는가 → 연구자는 연구 언어로 쓰고 평가위원은 지표 언어로 읽기 때문 → 그래서 가장 아픈 사람은 "제안서를 쓰는 사람" 일반이 아니라 **"제출 직전에 빈칸을 발견하는 사람"**이다. 우리는 제안서 생성이라는 넓은 문제 대신 이 장면 하나로 범위를 좁혔고, 비교축도 바꿨다: "얼마나 잘 쓰는가"가 아니라 **"평가위원이 볼 때 무엇이 비어 있는지를 얼마나 정확히 짚는가"**다.

# 2) 주요 내용 — AI Agent 제안 및 차별성 (5개 도구를 하나의 에이전트 루프로)

| 단계 | 에이전트가 하는 일 | 산출물 |
|---|---|---|
| ① RFP 파싱 | 공고문·첨부(PDF/HWPX)에서 자격 요건·필수 첨부·기간·평가지표·배점을 추출 | **요건 매트릭스** |
| ② 선행 탐색 | NTIS 과제·논문(OpenAlex/Semantic Scholar)·특허(KIPRIS) 검색 → 유사 과제와 차별점 요약 | **선행연구·특허 요약**(링크) |
| ③ 평가위원 시뮬레이션 | 관점이 다른 가상 평가위원 3~5명이 초안을 **독립** 채점 → 전원 감점(합의 결핍)과 의견 갈림(논쟁 지점) 분리 | **심사기준 대조표** |
| ④ 결핍 판정 | 지표를 뒷받침하는 문장·수치·선행과제가 없는 곳을 표시 | **결핍 목록** |
| ⑤ 보완 지정 | 결핍마다 넣어야 할 근거의 종류(수치·선행과제·일정)와 위치를 지정 | 보완 체크리스트 |

**기존 도구와 무엇이 다른가.**

| | 제안서 생성 도구 | 규정 체크리스트 | RFP-to-Fit |
|---|---|---|---|
| 1순위 출력 | 문장 | 요건 충족 여부 | **지표별 빈칸과 그 근거** |
| 심사자 관점 | 없음(단일 프롬프트) | 없음 | **관점이 다른 가상 평가위원의 합의·불일치** |
| 근거 | 선택 | 규정 원문 | **판정 결과 제시** |
| 연구자 역할 | 편집자 | 확인자 | **보완 체크리스트로 수정** |

**차별성의 핵심은 "관문 반대편을 모델링한다"는 데 있다.** 프롬프트 하나가 내는 점수 하나는 평가위원 한 명의 취향과 같다. 관점이 다른 여러 가상 평가위원이 독립 채점한 뒤 **모두가 감점한 항목만 "결핍"으로, 갈리는 항목은 "논쟁 지점"으로** 돌려주면, 연구자는 어디를 고쳐야 하고 어디는 취향 차이인지 5분 안에 안다. 이 구조는 보고서·정산 문서에도 그대로 적용된다(4절).

# 3) 구현방안

**활용 AI 기술 및 데이터.** 구조는 LLM + RAG + 도구 호출(MCP)이다. 추론·채점: Google Gemini API(본선 시점 최신 Pro/Flash 모델), 같은 인터페이스로 오픈소스 LLM(Qwen 계열) 교체 가능. 근거 검색(RAG): 임베딩 BAAI/bge-m3 + FAISS. 에이전트 루프: LangGraph. 문서 파싱: pdfplumber(PDF), HWPX는 ZIP+XML 직접 파싱. 외부 검색기(NTIS·KIPRIS·OpenAlex)는 MCP 도구 서버로 감싸 교체 가능하게 한다. 화면: Streamlit. 데이터는 전부 공개 자료다 — NTIS·IRIS 공개 공고·과제, KIPRIS 공개 특허(KIPRIS Plus API), OpenAlex·Semantic Scholar 공개 학술 API.

**시스템 구성·서비스 흐름.** [입력] 공고 URL/PDF/HWPX + 초안(선택) → [파서] 요건·지표 추출 → [탐색] MCP 도구로 선행과제·논문·특허 검색·요약 → [시뮬레이션] 가상 평가위원 N명 독립 채점 → [대조] 합의 결핍 / 논쟁 지점 분류 → [출력] 화면 한 장(요건 매트릭스·대조표·결핍 목록·보완 체크리스트). **정확도 목표(시연에서 공개)**: 공개 RFP 3건의 정답표 대비 요건 추출 재현율 90% 이상, 결핍 탐지 정밀도 80% 이상.

**해커톤 기간(무박 2일) 내 구현 계획.** 대회 전에는 개발하지 않는다 — 준비는 공개 RFP 3건 선정, 정답표 작성, API 키 발급, 종이 화면 설계까지. 1일차 17:00~24:00: ① 파서 + 요건 매트릭스(RFP 3건 검증), ② MCP 검색기 연결. 2일차 00:00~06:00: ③ 평가위원 시뮬레이션 + ④ 결핍 판정. 06:00~09:00: ⑤ 보완 지정 + Streamlit 화면 + 정확도 측정. 09:00~12:00: GitHub 정리·발표자료·리허설. **축소 규칙**: 1일차 24:00까지 ①이 3건 중 2건 이상 통과하지 못하면 ②를 링크 목록으로 줄이고 ③④에 시간을 몰아준다 — 핵심 시연은 대조표다. 역할: 대표(김태걸) 파서·에이전트 루프·정확도 측정, 팀원(박세훈) 화면·시연 시나리오·발표.

# 4) 기대효과 및 활용 가능성

- **연구자**: 결핍 발견 시점을 제출 직전에서 초안 단계로 앞당겨 형식 탈락과 지표 누락을 줄인다.
- **연구기관·연구지원 부서**: 기관 단위로 공고를 일괄 파싱해 "지원 가능 과제·부족 요건" 주간 대시보드로 확장. 출연연 연구지원부서 1곳 파일럿이 첫 실증 목표다.
- **성과 작성·연구행정(통합 주제)**: 같은 합의·불일치 엔진을 연차·성과 보고서(지표 대비 실적)와 연구비 정산(증빙 대비 항목)에 적용한다.
- **후속 연구**: 코드·정답표·평가 스크립트를 오픈소스(MIT)로 공개해 "RFP 결핍 벤치마크"를 만든다. 평가 데이터가 쌓이면 "어떤 결핍이 실제 탈락과 상관되는가"가 후속 연구 질문이 된다.
